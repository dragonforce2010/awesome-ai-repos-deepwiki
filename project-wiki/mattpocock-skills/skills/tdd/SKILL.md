# 测试驱动开发（Test-Driven Development）

## 理念

**核心原则**：测试应通过公共接口验证行为，而非实现细节。实现可整体替换；测试不应随之失效。

**好测试**偏集成风格：通过公共 API 走真实代码路径。它们描述系统**做什么**，而非**怎么做**。好测试读起来像规格——「用户可用有效购物车结账」清楚传达了存在的能力。此类测试在重构中存活，因其不关心内部结构。

**坏测试**与实现耦合。它们 mock 内部协作者、测试私有方法，或通过外部手段验证（例如绕过接口直接查库）。警示信号：你重构了但行为未变，测试却失败。若重命名内部函数导致测试失败，那些测试测的是实现而非行为。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 反模式：水平切片

**禁止**先写完全部测试再写完全部实现。这是「水平切片」——把 RED 当成「写所有测试」、GREEN 当成「写所有代码」。

这会产出**劣质测试**：

- 批量编写的测试验证的是**假想**行为，而非**真实**行为
- 最终测的是事物的**形状**（数据结构、函数签名），而非面向用户的行为
- 测试对真实变更不敏感——行为坏了仍通过，行为正确却失败
- 在理解实现之前就承诺测试结构，超出可视范围

**正确做法**：通过追踪弹（tracer bullet）做垂直切片。一个测试 → 一段实现 → 重复。每个测试回应上一轮所学。因为你刚写完代码，你清楚哪些行为重要以及如何验证。

```
错误（水平）：
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 工作流

### 1. 规划

探索代码库时使用项目领域词汇表，使测试命名与接口词汇与项目语言一致，并尊重相关 ADR。

在写任何代码前：

- [ ] 与用户确认需要哪些接口变更
- [ ] 与用户确认要测哪些行为（优先级）
- [ ] 识别 [deep modules](deep-modules.md) 的机会（小接口、深实现）
- [ ] 为 [testability](interface-design.md) 设计接口
- [ ] 列出要测的行为（非实现步骤）
- [ ] 获得用户对计划的批准

询问：「公共接口应是什么样？哪些行为最重要、必须测试？」

**无法测试一切。**与用户精确确认哪些行为最关键。把测试精力集中在关键路径与复杂逻辑，而非每个边缘情况。

### 2. 追踪弹（Tracer Bullet）

编写**一个**测试，确认关于系统的**一件事**：

```
RED:   为第一个行为写测试 → 测试失败
GREEN: 写最少代码使通过 → 测试通过
```

这是你的追踪弹——证明端到端路径可行。

### 3. 增量循环

对每个剩余行为：

```
RED:   写下一个测试 → 失败
GREEN: 最少代码使通过 → 通过
```

规则：

- 一次只加一个测试
- 仅写足够通过当前测试的代码
- 不要预判未来测试
- 保持测试聚焦于可观察行为

### 4. 重构

全部通过后，查找 [refactor candidates](refactoring.md)：

- [ ] 消除重复
- [ ] 加深模块（将复杂度藏到简单接口后）
- [ ] 在自然处应用 SOLID
- [ ] 思考新代码揭示了既有代码的什么
- [ ] 每步重构后运行测试

**禁止在 RED 时重构。**先到 GREEN。

## 每轮检查清单

```
[ ] 测试描述行为，而非实现
[ ] 测试仅使用公共接口
[ ] 测试在内部重构后仍能存活
[ ] 代码对当前测试而言最小化
[ ] 未添加臆测功能
```
