# 诊断（Diagnose）

应对疑难缺陷的纪律。除非有明确理由，否则不要跳过阶段。

在探索代码库时，使用项目的领域词汇表建立对相关模块的清晰心智模型，并查阅你正在改动区域的 ADR。

## 阶段 1 —— 建立反馈回路

**这就是本技能的核心。**其余步骤都是机械执行。如果你有一条快速、确定性的、可由代理运行的通过/失败信号来表征缺陷，你就能找到根因——二分、假设检验与插桩都只是消耗这条信号。如果你没有这条信号，再怎么盯着代码也无济于事。

在此阶段投入不成比例的努力。**要激进、要有创意、不要轻言放弃。**

### 构建信号的方式——大致按此顺序尝试

1. **失败用例**：无论单元、集成还是 e2e，只要能触达缺陷边界即可。
2. **Curl / HTTP 脚本**：对正在运行的开发服务器发起请求。
3. **CLI 调用**：使用夹具输入，将 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，对 DOM/控制台/网络做断言。
5. **重放已捕获的轨迹。**将真实网络请求 / 载荷 / 事件日志保存到磁盘；在隔离环境中重放该代码路径。
6. **一次性验证台。**拉起系统的最小子集（单服务、依赖 mock），用一次函数调用复现缺陷路径。
7. **属性 / 模糊测试循环。**若缺陷是「有时输出错误」，运行 1000 组随机输入寻找失败模式。
8. **二分验证台。**若缺陷出现在两个已知状态（提交、数据集、版本）之间，自动化「在状态 X 启动、检查、重复」，以便执行 `git bisect run`。
9. **差分循环。**同一输入在旧版 vs 新版（或两种配置）下运行并 diff 输出。
10. **人机协同 bash 脚本。**最后手段。若必须由人类点击，用 `scripts/hitl-loop.template.sh` 驱动**他们**，使循环仍有结构；捕获的输出再反馈给你。

构建正确的反馈回路，缺陷就算解决了九成。

### 对回路本身迭代

把回路当作产品。一旦有了**某种**回路，追问：

- 能否更快？（缓存初始化、跳过无关启动、收窄测试范围。）
- 信号能否更尖锐？（断言具体症状，而不是「没崩就算过」。）
- 能否更确定？（固定时间、固定 RNG 种子、隔离文件系统、冻结网络。）

30 秒一跑且 flaky 的回路几乎等于没有回路。2 秒一跑且确定性的回路是调试超能力。

### 非确定性缺陷

目标不是「干净复现」，而是**提高复现率**。将触发条件循环 100 次、并行加压、收窄时间窗、注入 sleep。50% 概率复现的缺陷仍可调试；1% 则不行——持续提高复现率直到可调试。

### 当你确实无法构建回路时

明确说明做不到。列出已尝试内容。向用户索要：(a) 能复现的环境访问权限，(b) 捕获产物（HAR、日志 dump、core dump、带时间戳的录屏），或 (c) 允许临时在生产环境插桩。在**没有回路**的情况下，**不要**进入假设阶段。

在你相信已有一条可用回路之前，不要进入阶段 2。

## 阶段 2 —— 复现

运行回路。观察缺陷出现。

确认：

- [ ] 回路产生的是**用户**所描述的失败形态——而不是碰巧附近的另一种失败。错缺陷 = 错修复。
- [ ] 失败在多次运行中可复现（对非确定性缺陷：复现率足够高以便继续调试）。
- [ ] 你已捕获确切症状（错误信息、错误输出、耗时变慢），以便后续阶段验证修复是否真正对症。

在复现缺陷之前，不要继续。

## 阶段 3 —— 提出假设

在验证任何假设之前，先生成 **3–5 条已排序的假设**。只生成一条假设容易锚定在第一个看似合理的想法上。

每条假设必须**可证伪**：写出它做出的预测。

> 格式：「若 <X> 是根因，则 <改变 Y> 会使缺陷消失 / <改变 Z> 会使其恶化。」

若无法陈述预测，该假设只是直觉——丢弃或收紧。

**在测试前向用户展示排序列表。**他们常有领域知识可瞬间重排（「我们刚部署了与 #3 相关的变更」），或知道哪些假设已排除。廉价检查点，大幅省时。不要阻塞——若用户不在，按你的排序继续。

## 阶段 4 —— 插桩

每次探测必须对应阶段 3 的某条具体预测。**一次只改变一个变量。**

工具偏好：

1. 若环境支持，优先 **调试器 / REPL 单步**。一个断点胜过十行日志。
2. 在能区分各假设的边界处打**定向日志**。
3. 禁止「到处打日志再 grep」。

**为每条调试日志打唯一前缀**，例如 `[DEBUG-a4f2]`。收尾时一次 grep 即可清理。无标签日志会残留；有标签日志应被清除。

**性能分支。**对性能回退，日志往往误导。应：先建立基线测量（计时台、`performance.now()`、分析器、查询计划），再二分。**先测量，后修复。**

## 阶段 5 —— 修复 + 回归测试

在修复**之前**写回归测试——但仅当存在**正确的接缝（seam）**时。

正确的接缝是指测试在**调用点真实复现缺陷模式**的位置。若唯一可用接缝过浅（缺陷需要多调用方却只用单调用方单测、单元测试无法复现触发缺陷的整条链），写在那里的回归测试只会制造虚假信心。

**若不存在正确接缝，这本身就是发现。**记录下来：代码库架构阻止把缺陷钉死。在下一阶段标记该结论。

若存在正确接缝：

1. 将最小化复现转为该接缝处的失败测试。
2. 观察失败。
3. 应用修复。
4. 观察通过。
5. 用原始（未最小化）场景重新运行阶段 1 的反馈回路。

## 阶段 6 —— 清理与事后总结

在宣布完成前必须满足：

- [ ] 原始复现路径不再复现（重跑阶段 1 回路）
- [ ] 回归测试通过（或已记录「无合适接缝」）
- [ ] 移除所有 `[DEBUG-...]` 插桩（按前缀 `grep`）
- [ ] 删除一次性原型（或移到明确标记的调试位置）
- [ ] 在提交 / PR 说明中写明最终被证实的假设——让下一位调试者受益

**然后追问：什么本可以预防这个缺陷？**若答案涉及架构变更（无合适测试接缝、调用方纠缠、隐藏耦合），在修复落地**之后**将具体细节交接给 `/improve-codebase-architecture` 技能——不要在此之前；你此时掌握的信息比开始时更多。
