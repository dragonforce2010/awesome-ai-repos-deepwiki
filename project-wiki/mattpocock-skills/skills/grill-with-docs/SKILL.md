## 领域意识

在探索代码库时，同时查找既有文档：

### 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

若根目录存在 `CONTEXT-MAP.md`，说明仓库有多个上下文。地图指明各自位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 全系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/                 ← 上下文专属决策
```

按需惰性创建文件——只有要写内容时才创建。若尚无 `CONTEXT.md`，在首个术语确定时再创建。若尚无 `docs/adr/`，在需要首份 ADR 时再创建。

## 会话过程中

### 对照词汇表挑战

当用户使用的术语与 `CONTEXT.md` 中的既有语言冲突时，立即指出。「词汇表将『cancellation』定义为 X，但你似乎指 Y——到底是哪一个？」

### 收紧模糊表述

当用户使用含糊或多义术语时，提出精确的规范用语。「你在说『account』——是指 Customer 还是 User？这是不同概念。」

### 讨论具体场景

在讨论领域关系时，用具体场景做压力测试。构造探查边界案例的场景，迫使用户精确说明概念之间的分界。

### 与代码交叉核对

当用户陈述某机制如何工作时，检查代码是否一致。若发现矛盾，抛出：「你的代码取消的是整张 Order，但你刚说支持部分取消——以哪边为准？」

### 内联更新 CONTEXT.md

术语一旦确定，立即更新 `CONTEXT.md`。不要批量延后——当场记录。格式见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

不要将 `CONTEXT.md` 与实现细节强耦合。只收录对领域专家有意义的术语。

### 谨慎提供 ADR

仅当以下**三者同时为真**时再提议创建 ADR：

1. **难以回滚**——日后改主意成本显著
2. **脱离上下文会显得意外**——未来读者会疑惑「为何如此设计」
3. **来自真实权衡**——存在可行替代方案，且因具体原因选择了当前方案

若任一条不成立，跳过 ADR。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
