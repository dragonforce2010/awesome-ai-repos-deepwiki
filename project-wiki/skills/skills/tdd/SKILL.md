# 测试驱动开发

## 理念

**核心原则**：测试应通过公开接口验证行为，而非实现细节。实现可以全盘更换；测试不该随之碎裂。

**好测试**偏集成风格：经由真实代码路径、公开 API 演练。描述系统**做什么**，而非**怎么做**。好测试读起来像规格——「用户可用有效购物车结账」清楚交代了能力。重构后仍站得住，因其不关心内部结构。

**坏测试**与实现耦合： mock 内部协作者、测私有方法，或通过外部手段验证（例如不经过接口直接查库）。警讯：重构后测试失败但行为未变。若重命名内部函数导致测试失败，那些测试测的是实现而非行为。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 反模式：水平切片

**不要先写完全部测试再写完全部实现。** 这是「水平切片」——把 RED 当成「写所有测试」、GREEN 当成「写所有代码」。

会产出**垃圾测试**：

- 批量写的测试验证的是**想象**行为，不是**实际**行为
- 往往测的是**形状**（数据结构、函数签名）而非面向用户的行为
- 对真实变更不敏感——行为坏了仍过、行为正常却失败
- 在理解实现前就固化测试结构，**超出能见范围**

**正确做法**：用追踪弹做垂直切片。一个测试 → 一段实现 → 重复。每个测试回应上一轮学到的东西。刚写过实现，你最清楚哪些行为重要、如何验证。

```
错误（水平）：
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 工作流

### 1. 规划

探索代码库时使用项目领域词汇表，使测试命名与接口词汇与项目语言一致，并尊重所涉区域的 ADR。

写任何代码前：

- [ ] 与用户确认需要哪些接口变更
- [ ] 与用户确认要测哪些行为（优先级）
- [ ] 识别 [deep modules](deep-modules.md) 机会（小接口、深实现）
- [ ] 为 [testability](interface-design.md) 设计接口
- [ ] 列出要测的行为（非实现步骤）
- [ ] 取得用户对计划的认可

询问：「公开接口应长什么样？哪些行为最值得测？」

**你测不了所有东西。** 与用户确认究竟哪些行为最关键。把测试精力放在关键路径与复杂逻辑，而非每个边角。

### 2. 追踪弹

写一个测试，只确认系统的一件事：

```
RED:   为首个行为写测试 → 失败
GREEN: 写最少代码通过 → 通过
```

这是追踪弹——端到端证明路径可走。

### 3. 增量循环

对其余每个行为：

```
RED:   写下一个测试 → 失败
GREEN: 最少代码通过 → 通过
```

规则：

- 一次一个测试
- 仅够通过当前测试的代码
- 不要预知未来测试
- 测试聚焦可观察行为

### 4. 重构

全部通过后，寻找 [refactor candidates](refactoring.md)：

- [ ] 消除重复
- [ ] 加深模块（把复杂度移到简单接口之后）
- [ ] 在自然处应用 SOLID
- [ ] 思考新代码揭示了旧代码的什么
- [ ] 每步重构后跑测试

**不要在 RED 时重构。** 先到 GREEN。

## 每轮检查清单

```
[ ] 测试描述行为而非实现
[ ] 测试仅使用公开接口
[ ] 内部重构后测试仍应成立
[ ] 代码对本测试而言最简
[ ] 未添加臆测功能
```
