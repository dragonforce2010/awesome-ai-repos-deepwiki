# 诊断

适用于困难缺陷的纪律。仅在有明确理由时跳过阶段。

在浏览代码库时，使用项目的领域词汇表建立相关模块的心智模型，并查看所涉及区域的 ADR。

## 阶段 1 — 建立反馈回路

**这就是本 skill 的核心。**其余都是机械步骤。若你对该缺陷有快速、确定、可由代理执行的通过/失败信号，你就能找到根因——二分、假设检验与插桩只是消费该信号。若没有信号，盯代码再久也救不了你。

在此阶段投入不成比例的努力。**要积极、要敢想、不轻易放弃。**

### 构建回路的方式 — 大致按此顺序尝试

1. 在能触达缺陷的任意接缝处写**失败测试**——单元、集成或端到端。
2. 对已运行的开发服务器执行 **Curl / HTTP 脚本**。
3. 带固定输入的 **CLI 调用**，将 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/console/network 断言。
5. **重放已捕获的轨迹。** 将真实网络请求 / 负载 / 事件日志存盘；在隔离环境中重放穿过代码路径。
6. **一次性 harness。** 拉起系统的最小子集（单服务、模拟依赖），用单次函数调用触发缺陷路径。
7. **属性 / 模糊循环。** 若缺陷是「有时输出错误」，跑 1000 个随机输入寻找失败模式。
8. **二分 harness。** 若缺陷出现在两个已知状态（提交、数据集、版本）之间，自动化「在状态 X 启动、检查、重复」以便 `git bisect run`。
9. **差分循环。** 同一输入跑旧版 vs 新版（或两种配置）并 diff 输出。
10. **HITL bash 脚本。** 最后手段。若必须由人点击，用 `scripts/hitl-loop.template.sh` **驱动他们**，使循环仍有结构。捕获的输出再反馈给你。

选对反馈回路， bug 就修了九成。

### 迭代回路本身

把回路当作产品。一旦有了**某种**回路，追问：

- 能更快吗？（缓存安装、跳过无关初始化、缩小测试范围。）
- 信号能更尖锐吗？（断言具体症状，而非「没崩溃」。）
- 能更确定吗？（固定时间、固定 RNG 种子、隔离文件系统、冻结网络。）

30 秒一次的 flaky 回路几乎等于没有。2 秒一次的确定回路是调试超能力。

### 非确定缺陷

目标不是干净复现，而是**更高的复现率**。循环触发 100 次、并行、加压、收窄时间窗、注入 sleep。50% 抖动的 bug 可调试；1% 不行——持续提高率直到可调试。

### 当你确实无法建立回路时

停下并明确说明。列出已尝试项。向用户索要：(a) 能复现的环境访问，(b) 捕获物（HAR、日志转储、core dump、带时间戳的录屏），或 (c) 允许添加临时生产插桩。**没有回路就不要进入假设阶段。**

在拥有可信回路之前，不要进入阶段 2。

## 阶段 2 — 复现

运行回路。观察缺陷出现。

确认：

- [ ] 回路产生**用户**描述的失败模式——而非碰巧附近的另一种失败。错 bug = 错修复。
- [ ] 失败在多次运行中可复现（或非确定缺陷以足够高的比率复现以便对其调试）。
- [ ] 你已捕获确切症状（错误信息、错误输出、缓慢耗时），以便后续阶段验证修复确实针对该问题。

在复现缺陷之前不要继续。

## 阶段 3 — 假设

在检验任一条之前，先生成 **3–5 条排序后的假设**。单条假设容易锚定第一个看似合理的想法。

每条假设必须**可证伪**：陈述其预测。

> 格式：「若 <X> 是原因，则 <改变 Y> 会使缺陷消失 / <改变 Z> 会使其恶化。」

若无法陈述预测，这条假设是「感觉」——丢弃或收紧。

**在测试前向用户展示排序列表。** 他们常有能瞬间重排的领域知识（「我们刚对 #3 部署了变更」），或知道已排除的假设。低成本检查点，省大量时间。若用户 AFK 不必阻塞——按你的排序继续。

## 阶段 4 — 插桩

每次探测必须对应阶段 3 的某条具体预测。**一次只改变一个变量。**

工具偏好：

1. 若环境支持，优先 **调试器 / REPL 单步**。一个断点胜过十行日志。
2. 在能区分假设的边界打**定向日志**。
3. 绝不「全盘打日志再 grep」。

**给每条调试日志打唯一前缀**，例如 `[DEBUG-a4f2]`。收尾时一次 grep 即可清理。无标签的日志会存活；有标签的应删除。

**性能分支。** 对性能回退，日志通常不对。应：先建立基线测量（计时 harness、`performance.now()`、分析器、查询计划），再二分。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

在修复**之前**写回归测试——但仅当存在**正确的接缝**时。

正确的接缝是指测试在调用点演练**真实的缺陷模式**。若唯一可用接缝太浅（多调用者场景下却做单调用者测试、无法复现触发链的单元测试），那里的回归测试会给出虚假信心。

**若没有正确接缝，这本身就是发现。** 记下它。代码库架构阻止将该 bug 锁住。在下一阶段标出。

若存在正确：

1. 将最小化复现变成该接缝处的失败测试。
2. 观察失败。
3. 应用修复。
4. 观察通过。
5. 用原始（未最小化）场景重新跑阶段 1 的反馈回路。

## 阶段 6 — 清理 + 事后总结

在宣称完成前必须：

- [ ] 原始复现不再出现（重跑阶段 1 回路）
- [ ] 回归测试通过（或已记录缺少接缝）
- [ ] 移除所有 `[DEBUG-...]` 插桩（`grep` 该前缀）
- [ ] 删除一次性原型（或移到明确标记的调试位置）
- [ ] 在提交 / PR 信息中写明**最终被证实**的假设——让下一个调试者受益

**然后问：什么能预防此类 bug？** 若答案涉及架构变更（没有好的测试接缝、调用方纠缠、隐藏耦合），在修复落地**之后**把具体情况交给 `/improve-codebase-architecture` skill。建议在**修复之后**再推荐——此时信息比开始时更多。
