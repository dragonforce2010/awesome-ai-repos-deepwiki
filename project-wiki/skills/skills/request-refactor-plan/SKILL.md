---

当用户要创建重构请求时会触发本技能。按下列步骤执行；若某步你认为不必要可跳过。

1. 请用户用较长、较细的篇幅描述要解决的问题以及可能想到的解法。

2. 探索仓库以核实其判断，并理解代码库当前状态。

3. 询问是否考虑过其他选项，并向其展示其他可选路径。

4. 就实现方案访谈用户，务必足够细、足够全。

5. 敲定实现的确切范围：计划改什么、计划不改什么。

6. 在代码库中查看该区域的测试覆盖；若不足，询问用户的测试打算。

7. 将实现拆成「极小提交」的计划。牢记 Martin Fowler 的建议：「每一步重构都尽量小，这样你始终能看到程序仍在工作。」

8. 用重构计划创建 GitHub Issue。Issue 描述使用下列模板：

<refactor-plan-template>

## 问题陈述

从开发者视角描述其面临的问题。

## 方案

从开发者视角描述问题的解决方案。

## 提交计划

一份很长、很细的实施计划。用平实语言书写，把实现拆成尽可能小的提交；每个提交都应让代码库保持可运行。

## 决策文档

已做出的实现决策列表，可包括：

- 将新建/修改的模块
- 这些模块将被修改的接口
- 来自开发者的技术澄清
- 架构决策
- 模式（schema）变更
- API 契约
- 具体交互

不要包含具体文件路径或代码片段——它们会很快过时。

## 测试决策

已做出的测试决策列表，需包含：

- 何为好的测试（只测对外行为，不测实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中相近类型的测试）

## 不在范围内

说明本次重构不包含的内容。

## 其他说明（可选）

关于本次重构的其他说明。

</refactor-plan-template>
