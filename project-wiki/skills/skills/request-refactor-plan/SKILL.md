description: 通过用户访谈创建含微小提交的详细重构计划，并提交为 GitHub issue。在用户希望规划重构、撰写重构 RFC，或将重构拆成安全增量步骤时使用。
---

当用户希望创建重构请求时运行本 skill。按下方步骤执行。若认为不必可跳过步骤。

1. 请用户提供要写长文的问题描述及任何初步解决思路。

2. 探索仓库以验证其说法并理解代码库现状。

3. 询问是否考虑过其它选项，并向其展示其它选项。

4. 就实现细节访谈用户。要极其详尽。

5. 敲定实现的确切范围。明确将改什么、不改什么。

6. 在代码库中查看该区域的测试覆盖。若不足，询问用户测试计划。

7. 将实现拆成**微小提交**的计划。谨记 Martin Fowler：「每一步重构尽量小，以便始终能看到程序仍在工作。」

8. 用以下模板创建含重构计划的 GitHub issue：

<refactor-plan-template>

## Problem Statement

从开发者视角，开发者面临的问题。

## Solution

从开发者视角，问题的解决方案。

## Commits

**长而详尽的**实现计划。用 plain English 书写，将实现拆成尽可能小的提交。每个提交都应让代码库处于可工作状态。

## Decision Document

已做出的实现决策列表，可包括：

- 将构建/修改的模块
- 将修改的那些模块的接口
- 开发者确认的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

**不要**包含具体文件路径或代码片段——它们会很快过时。

## Testing Decisions

测试决策列表，包含：

- 何为好的测试（只测对外行为，不测实现细节）
- 将测试哪些模块
- 测试先例（代码库中类似测试）

## Out of Scope

本重构范围之外的内容说明。

## Further Notes (optional)

关于本重构的其它说明。

</refactor-plan-template>
