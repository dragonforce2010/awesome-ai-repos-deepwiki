# 改进代码库架构

暴露架构摩擦并提出**加深机会**——将浅层模块重构为更深层的重构。目标是可测试性与 AI 可导航性。

## 词汇表

每条建议中**精确**使用下列术语。语言一致才是重点——不要滑向「组件」「服务」「API」或「边界」。完整定义见 [LANGUAGE.md](LANGUAGE.md)。

- **模块（Module）** —— 任何带接口与实现的事物（函数、类、包、切片）。
- **接口（Interface）** —— 调用方使用模块必须了解的一切：类型、不变量、错误模式、顺序、配置。不仅是类型签名。
- **实现（Implementation）** —— 内部的代码。
- **深度（Depth）** —— 接口处的杠杆：大量行为藏在小型接口之后。**深** = 高杠杆。**浅** = 接口几乎与实现一样复杂。
- **接缝（Seam）** —— 接口所在之处；可在不就地编辑的情况下改变行为的位置。（用此词，不要用「边界」。）
- **适配器（Adapter）** —— 在接缝处满足接口的具体事物。
- **杠杆（Leverage）** —— 调用方从深度中获得的东西。
- **局部性（Locality）** —— 维护者从深度中获得的东西：变更、缺陷、知识集中在一处。

关键原则（完整列表见 [LANGUAGE.md](LANGUAGE.md)）：

- **删除测试**：想象删除该模块。若复杂度消失，它是透传。若复杂度分散到 N 个调用方，它才物有所值。
- **接口即测试表面。**
- **一个适配器 = 假想接缝。两个适配器 = 真实接缝。**

本 skill 受项目**领域模型**导引。领域语言为好接缝命名；ADR 记录本 skill 不应重开的决策。

## 流程

### 1. 探索

先读项目领域词汇表及你所涉区域的任意 ADR。

然后用 Agent 工具 `subagent_type=Explore` 遍历代码库。不要僵化启发式——有机探索并记下感到摩擦之处：

- 理解一个概念是否要在许多小模块间跳来跳去？
- 哪里模块**偏浅**——接口几乎与实现一样复杂？
- 是否仅为可测试性抽出纯函数，但真正缺陷藏在调用方式中（没有**局部性**）？
- 紧耦合模块是否在接缝间渗漏？
- 哪些部分未测试或通过当前接口难以测试？

对任何疑似浅层模块做**删除测试**：删除它会集中复杂度，还是只是挪动？「会集中」才是你要的信号。

### 2. 呈现候选

列出编号的加深机会。对每个候选：

- **文件** —— 涉及哪些文件/模块
- **问题** —— 当前架构为何造成摩擦
- **方案** —— _plain English_ 说明将改变什么
- **好处** —— 用局部性与杠杆说明，并说明测试会如何改善

**领域用 `CONTEXT.md` 词汇，架构用 [LANGUAGE.md](LANGUAGE.md) 词汇。** 若 `CONTEXT.md` 定义了「Order」，谈「Order 摄入模块」——而非「FooBarHandler」，亦非「Order 服务」。

**与 ADR 冲突**：若候选与既有 ADR 矛盾，仅当摩擦足够大、值得重审 ADR 时再提出。标注清楚（例如 _「与 ADR-0007 冲突——但值得重开，因为…」_）。不要列出 ADR 禁止的每个假想重构。

**尚不要提出接口设计。** 询问用户：「你想深入探讨其中哪一个？」

### 3. 拷问循环

用户选定候选后，进入拷问对话。与对方一起沿设计树推进——约束、依赖、加深后模块的形态、接缝背后是什么、哪些测试保留。

副作用随决策成形内联发生：

- **将加深模块命名为 `CONTEXT.md` 中尚无的概念？** 把术语加入 `CONTEXT.md`——与 `/grill-with-docs` 同一纪律（见 [CONTEXT-FORMAT.md](../grill-with-docs/CONTEXT-FORMAT.md)）。若文件不存在则惰性创建。
- **对话中收紧模糊术语？** 当场更新 `CONTEXT.md`。
- **用户以承重理由拒绝候选？** 提供 ADR，框架为：_「要不要记成 ADR，免得未来架构评审再提同一建议？`_ 仅当未来探索者确实需要该理由才能避免重复建议时提供——跳过 ephemeral（「现在不值当」）与自明理由。见 [ADR-FORMAT.md](../grill-with-docs/ADR-FORMAT.md)。
- **想为加深模块探索备选接口？** 见 [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md)。
