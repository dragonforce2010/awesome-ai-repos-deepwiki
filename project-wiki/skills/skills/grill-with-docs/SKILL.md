## 领域感知

在探索代码库时，同时查找既有文档：

### 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

若根目录存在 `CONTEXT-MAP.md`，仓库有多个上下文。地图指明各自位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 全系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性创建文件——有内容要写时再建。若没有 `CONTEXT.md`，在首个术语敲定时创建。若没有 `docs/adr/`，在需要首条 ADR 时再建。

## 会话过程中

### 对照词汇表挑战

当用户使用的术语与 `CONTEXT.md` 中的语言冲突时，立即指出。「你的词汇表把『取消』定义为 X，但你似乎指 Y——到底是哪一个？」

### 收紧模糊表述

当用户使用含糊或多义术语时，提出精确的规范用语。「你说『账户』——是指 Customer 还是 User？这是不同概念。」

### 讨论具体场景

讨论领域关系时，用具体场景做压力测试。发明能探边、迫使用户精确界定概念边界的场景。

### 与代码交叉核对

当用户陈述某物如何工作时，检查代码是否一致。若发现矛盾，抛出：「你的代码取消的是整个 Order，但你刚说可以部分取消——以哪边为准？」

### 内联更新 CONTEXT.md

术语敲定后，立即更新 `CONTEXT.md`。不要攒批——当场记录。格式见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

不要将 `CONTEXT.md` 与实现细节耦合。只收录对领域专家有意义的术语。

### 谨慎提供 ADR

仅当三者同时为真时才建议 ADR：

1. **难以回滚**——日后改主意的成本显著
2. **脱离上下文会令人惊讶**——未来读者会想「为什么这么做？」
3. **真实权衡的结果**——确有备选方案且因具体原因选定其一

若任一不满足，跳过 ADR。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
