# 系统化调试

## 概述

随机修复浪费时间并制造新 bug。快速补丁掩盖底层问题。

**核心原则：**始终在尝试修复之前找到根因。症状修复就是失败。

**违反此流程的字面意思就是违反调试的精神。**

## 铁律

```
没有根因调查就不能提出修复
```

如果你还没完成第一阶段，你不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别在以下情况使用：**
- 时间压力下（紧急情况使猜测变得诱人）
- "只需一个快速修复"看起来很明显
- 你已经尝试了多个修复
- 之前的修复没起作用
- 你不完全理解问题

**不要跳过：**
- 问题看起来简单（简单 bug 也有根因）
- 你很着急（系统化比胡乱尝试更快）
- 经理要求现在就修（系统化比混乱更快）

## 四个阶段

你必须完成每个阶段后才能进入下一个。

### 阶段一：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息** — 不要跳过错误或警告，它们通常包含精确解决方案
2. **稳定复现** — 能可靠触发吗？精确步骤是什么？每次都发生吗？不可复现 → 收集更多数据，不要猜测
3. **检查最近变更** — 什么变更可能导致这个问题？git diff、最近提交、新依赖、配置变更、环境差异
4. **在多组件系统中收集证据** — 在每个组件边界添加诊断，运行一次收集证据，定位失败组件
5. **追踪数据流** — 坏值从哪里来？什么传入了坏值？一直追溯到源头。在源头修复，而非症状

### 阶段二：模式分析

**在修复之前找到模式：**

1. 找到同类工作的代码
2. 完整阅读参考实现（不要略读 — 逐行阅读）
3. 列出每个差异，无论多小
4. 理解所有依赖

### 阶段三：假设与测试

**科学方法：**

1. **形成单一假设** — 明确陈述："我认为 X 是根因，因为 Y"
2. **最小化测试** — 做最小变更来测试假设，一次一个变量
3. **验证后继续** — 起作用了吗？是 → 阶段四。没起作用？形成新假设。不要叠加修复
4. **不懂就说不懂** — 不要假装知道，请求帮助，做更多研究

### 阶段四：实施

**修复根因，而非症状：**

1. **创建失败测试用例** — 最简单的复现，使用 `superpowers:test-driven-development` 技能
2. **实施单一修复** — 解决识别的根因，一次一个变更，不"顺便"改进
3. **验证修复** — 测试现在通过了吗？其他测试没坏？问题真的解决了？
4. **如果修复不起作用** — 停止。数一数你尝试了多少次修复。如果 < 3：回到阶段一，用新信息重新分析。**如果 ≥ 3：停止并质疑架构（步骤 5）**。不要在没有架构讨论的情况下尝试第 4 次修复
5. **如果 3+ 次修复失败：质疑架构** — 每次修复在不同地方暴露新的共享状态/耦合/问题，修复需要"大规模重构"才能实施，每次修复在其他地方创建新症状 → 这是错误的架构，不是失败的假设。在尝试更多修复之前与你的用户伙伴讨论

## 红旗 - 停止并遵循流程

如果你发现自己在想：
- "先快速修复，稍后调查"
- "试试改 X 看看是否有效"
- "添加多个变更，运行测试"
- "跳过测试，我手动验证"
- "可能是 X，让我修复那个"
- "我不完全理解但这可能有效"
- "模式说 X 但我会不同地适配"
- "主要问题是：[列出修复而非调查]"
- 在追踪数据流之前提出解决方案
- **"再试一次修复"（已经尝试 2+ 次时）**
- 每次修复在不同地方暴露新问题

**所有这些都意味着：停止。回到阶段一。**

**如果 3+ 次修复失败：**质疑架构（见阶段四第 5 步）

## 常见合理化

| 借口 | 现实 |
|------|------|
| "问题简单，不需要流程" | 简单问题也有根因。流程对简单 bug 很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜测式混乱更快。 |
| "先试试这个，然后调查" | 第一次修复设定模式。从一开始就做对。 |
| "确认修复有效后再写测试" | 未经测试的修复不会持久。先写测试证明它。 |
| "多个修复同时进行节省时间" | 无法隔离什么起作用了。还会制造新 bug。 |
| "参考太长，我会适配模式" | 部分理解保证出 bug。完整阅读。 |
| "我看到问题了，让我修复" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要再次修复。 |
