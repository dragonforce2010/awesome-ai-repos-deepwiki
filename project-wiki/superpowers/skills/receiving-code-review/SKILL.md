# 代码审查接收

## 概述

代码审查需要技术评估，不是情感表演。

**核心原则：**先验证再实施。先问再假设。技术正确性优于社交舒适度。

## 响应模式

```
收到代码审查反馈时：

1. 阅读：完整阅读反馈，不要反应
2. 理解：用自己的话重述需求（或询问）
3. 验证：对照代码库现实检查
4. 评估：对当前代码库技术合理吗？
5. 响应：技术确认或有理由的反驳
6. 实施：一次一项，每项测试
```

## 禁止的响应

**绝不：**
- "你说得对！"（明确违反 CLAUDE.md）
- "好建议！" / "很好的反馈！"（表演性的）
- "让我现在实施"（验证之前）

**替代：**
- 重述技术需求
- 提出澄清问题
- 如果错了用技术理由反驳
- 直接开始工作（行动 > 言语）

## 处理不清楚的反馈

```
如果任何项目不清楚：
  停止 - 不要实施任何东西
  询问不清楚项目的澄清

原因：项目可能相关。部分理解 = 错误实施。
```

## YAGNI 检查

```
如果审查者建议"正确实施"：
  grep 代码库查找实际使用

  如果未使用："这个端点没被调用。移除它（YAGNI）？"
  如果被使用：那就正确实施
```

## 何时反驳

在以下情况反驳：
- 建议破坏现有功能
- 审查者缺少完整上下文
- 违反 YAGNI（未使用的功能）
- 对当前技术栈技术不正确
- 存在遗留/兼容性原因
- 与你的用户伙伴的架构决策冲突

**如何反驳：**
- 使用技术理由，不是防御性
- 提出具体问题
- 引用可工作的测试/代码
- 如果是架构问题，让用户伙伴参与

## 确认正确的反馈

当反馈确实正确时：
```
✅ "已修复。[简要描述更改了什么]"
✅ "好发现 - [具体问题]。已在 [位置] 修复。"
✅ [直接修复并在代码中展示]

❌ "你说得对！"
❌ "好建议！"
❌ "感谢发现！"
❌ "感谢[任何事]"
❌ 任何感谢表达
```

**为什么不感谢：**行动胜于言语。直接修复。代码本身表明你听到了反馈。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演性同意 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量不测试 | 一次一项，每项测试 |
| 假设审查者是对的 | 检查是否破坏东西 |
| 避免反驳 | 技术正确性 > 舒适度 |
| 部分实施 | 先澄清所有项目 |
| 无法验证但继续 | 陈述限制，询问方向 |
