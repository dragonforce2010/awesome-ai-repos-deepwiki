# build-page-mock

当任务是创建、修改、评审或根据需要让用户在浏览器中体验的页面 Mock / 原型 / 交互式 Demo 进行实现时，使用此技能。

典型触发词：
- 用户要求进行 `页面 Mock` / `页面原型` / `高保真原型` / `可交互 demo`
- 在真实后端就绪前，用户要求提供可在浏览器中运行的预览页面
- 用户要求 `按 mock 落产品` / `从 mock 生成页面` / `按原型实现最终页面`
- 涉及的文件包含 `docs/draft/*mock*.html`、`web/src/**` 预览路由或 `internal/app/daemon/adminui/**` mock 页面

## 前置阅读

编辑前阅读以下文档：
- `docs/general/page-mock-guidelines.md`
- `docs/general/web-design-guidelines.md`

## 强制执行顺序

在编辑页面前，必须为自己锁定以下五个项：
1. 最终用户是谁？
2. 当前该页面正在服务哪一个单一任务？
3. 允许在页面上呈现哪些信息类型？
4. 不允许在页面上呈现哪些信息类型？
5. 允许哪些反馈槽（Feedback Slots）显示成功 / 校验 / 错误 / 回退？

这被视为该页面的可见内容契约。在契约明确之前，禁止开始编写可见的页面内容。

## 规则

### 1. 将 Mock 视为最终用户产物
- 渲染的页面必须仅显示面向最终用户的内容。
- 不得在页面中渲染 `mock`、`demo`、`prototype`、`wireframe`、`设计说明`、`TODO` 或其他内部用语。
- 这包括浏览器标题、页面头部、帮助文本、占位符、空状态、通知和调试面板。
- 此规则同样适用于伪数据和演示数据，而不仅限于固定文案。

### 1.1 可见内容默认采用 Fail-Closed 策略
- 只有明确属于可见内容契约的内容才能在屏幕上呈现。
- 如果无法证明某个可见元素对最终用户完成当前页面的任务有何帮助，请将其移除。
- 不要仅仅因为是样例数据、说明性数据或易于复用而保留可疑内容。
- 当页面并非明确用于工程、调试或运维诊断时，代码、仓库路径、内部对象名称、协议字段和实现说明默认都是禁止呈现的。

### 2. 保持可运行，而非仅具说明性
- Mock 必须可以在浏览器中运行。
- 静态截图或死 HTML 不算数。
- 只有在真正具备交互性且可在浏览器中运行时，独立的 HTML 才是可接受的。
- 如果仓库中已经存在适合该任务的 App 外壳或路由模型，优先将其集成，而不是构建脱节的静态产物。

### 3. 伪数据仅用于覆盖真实的交互
- 在缺少后端时，可以自由使用伪数据。
- 覆盖页面所暴露的每一个用户可编辑、可选择、可过滤、可搜索或可导航的数据界面。
- 如果用户可以到达空 / 有数据 / 校验 / 成功 / 失败状态，请使这些状态在 Mock 中均可触发。
- 伪数据必须同样遵守可见内容契约。
- 不得将源码、仓库路径、内部状态名称、调试输出或设计说明用作可见的示例内容，除非页面契约明确允许这些技术内容。

### 4. 覆盖反馈契约，而仅是 Happy Path
- 针对每一个关键的用户操作，使相关的反馈状态在 Mock 中可触达。
- 至少考虑以下状态的所需子集：
  - 加载中 (loading)
  - 成功 (success)
  - 校验错误 (validation error)
  - 可恢复的业务错误 (recoverable business error)
  - 瞬时系统错误 (transient system error)
  - 空状态 / 无权限 / 已过期（若适用）
- Mock 不需要包含每一个确切的后端错误字符串。
- Mock 必须定义反馈呈现的位置以及用户接下来的操作。

### 5. 每一个可见的交互都必须是真实的
- 按钮、标签页、对话框、表单、折叠面板、导航、搜索、过滤器、排序、分页和多步流程都必须改变真实的页面状态。
- 不要留下无响应的“死”控件。
- 如果后端操作尚不存在，用本地状态、伪服务或浏览器内确定性行为进行模拟，而不是无操作（no-op）。

### 6. 响应式表现是交付物的一部分
- 验证桌面端和移动端。
- 验证宽度变化以及横竖屏切换。
- 如果布局或导航应该根据断点或方向进行区分，在 Mock 中实现这些表现。
- 不要依赖单一的静态视口。

### 7. 批准的 Mock 是真实产品的用户可见契约
- 在根据批准 of Mock 实现真实产品时，使用户可见的结构、文案、状态、交互路径、反馈槽以及响应式表现与该 Mock 保持一致。
- 允许的主要差异是替换伪业务数据以及在批准的反馈槽内将 Mock 反馈示例替换为真实的运行时反馈实例。
- 在实现期间，不要仅仅因为后端、校验或边缘情况更复杂而增加额外的用户可见文案。
- 在实现期间，不要发明新的用户可见错误区域或回退块。
- 如果后端返回的错误未在 Mock 中精确列出，将其引导到页面批准的通用回退槽中，而不是增加新的展现面。
- 如果必须修改用户可见契约，首先更新 Mock 或规范指南，再更新产品。

## 交付清单

在结束前，验证：
1. 没有遗留任何用户可见的设计意图用语。
2. 产物可在浏览器中运行。
3. 所有可见控件和流程均能正常工作。
4. 伪数据覆盖了页面的完整交互面。
5. 关键用户操作包含了可触发的反馈状态，而仅是 happy path。
6. 在批准的反馈槽内定义了通用回退表现。
7. 桌面、移动端及横竖屏切换保持可用。
8. 如果是根据批准的 Mock 实现，真实产品除业务数据和批准槽内的运行时反馈实例外，在所有用户可见方面仍与该 Mock 一致。
9. 存在可见内容契约：最终用户、当前任务、允许的信息类型、禁止的信息类型以及允许的反馈槽。
10. 每一个可见的字符串、标签、占位符、示例值、列表项和通知均能基于该契约进行证明。
11. 没有可见的示例数据意外泄露代码、仓库结构、内部名称、协议字段或其他面向工程的内容，除非这明确是该页面面向用户的目的。
12. 如果有任何可见内容感觉可疑，除非契约明确允许，否则已被移除。

如果其中一项失败，则 Mock 尚未完成。
