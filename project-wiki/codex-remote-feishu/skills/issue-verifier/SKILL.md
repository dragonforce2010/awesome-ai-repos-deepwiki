# Issue Verifier

在实现基本稳定后，使用此技能进行独立的验收轮次。

默认进行只读评审。除非用户在唯一步骤中明确要求修复，否则不要默默继续实现。

如果 Issue 仍在构思中、仍缺少执行闭环，或处于实现中期，将控制权交回给 `$issue-workflow-guardrail`，而不是强行提前验证。

## 阅读顺序

按以下顺序进行评审：
1. issue 描述主体
2. 维护者或用户的最新评论
3. 链接的设计文档和验收参考
4. 改动的文件 / diff / 验证证据
5. 如果关闭在范围内，检查当前工作区状态和发布状态

当最新的维护者或用户指示与旧的 issue 主体文字发生冲突时，以最新指示为准。

## 验证清单

明确验证以下维度：
- 目标对齐
  - 实现是否解决了 issue 声明的目标
- 非目标约束
  - 实现是否漂移到了有意排除的区域
- 验收覆盖
  - 每一个验收项是否都满足，是否有遗漏
- 回归面
  - 是否存在未经验证的风险路径或可能的回归 bug
- 长效知识同步
  - 是否应该更新 issue 主体、docs、状态机文档、AGENTS 或 skills
- 关闭就绪度
  - issue 是否真正准备好关闭，或者仅在本地完成

如果 issue 是中/大型，还需检查父/子 issue 边界是否保持连贯，以及推迟的跟进工作是否记录在长效位置。

如果当前是父 issue，还需明确检查：
- 每一个完成的子 issue 是否都已长效合并回父 issue
- 父 issue 的全局视图是否展示了汇总状态、验证器状态和当前的关闭判断

如果当前是子 issue，还需明确检查：
- 父 issue 链接是否已长效记录
- 子 issue 的结果在关闭前是否已长效合并回父 issue

## 输出格式

使用结论先行的评审风格。

期望的格式：
- 第一行：固定的验证器结果记录
  - `独立 verifier 结果：pass`
  - `独立 verifier 结果：pass with gaps`
  - `独立 verifier 结果：fail`
- 结论先行
  - 按严重程度排序
  - 当结论针对特定代码时包含文件引用
- 随后是开放性问题或假设
- 随后是 pass/fail 建议
  - `pass`
  - `pass with gaps`
  - `fail`
- 随后是简短的关闭说明
  - 关闭前还剩下什么
  - 是否缺少长效知识同步

`pass with gaps` 意味着 issue 尚未准备好关闭。这些差距必须在关闭前长效记录。

## 安全红线

- 不要因为修复看起来很明显就默默修改代码。
- 不要把验收差距降级为风格建议。
- 除非用户在验证器运行中明确要求，否则不要自己关闭 issue。
- 如果验证器只发现琐碎、明确受限的差距，先进行报告；实现可以在随后的步骤中进行。
- 如果 issue 缺少足够长效的上下文来支撑干净的验证，说明该 issue 需要重新梳理或关闭索引修复，并将其交回给 `$issue-workflow-guardrail`。
